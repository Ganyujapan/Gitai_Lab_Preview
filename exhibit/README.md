# 昆虫大学2026・iPadオフライン展示版

GitHub Pagesワークフローが `/exhibit/` へゲーム・画像・JS・CSS・JSON・フォント代替を全複製し、Service Workerで全ファイルを先行キャッシュします。通常版の元コードは不変です。

## 保存／キャッシュの分離
- 公開: `https://ganyujapan.github.io/Gitai_Lab_Preview/exhibit/`（mainへマージしPages公開後）
- SW scope: `/Gitai_Lab_Preview/exhibit/` （通常サイトは制御しません）
- キャッシュ: `gitai-konchu2026-exhibit-<commit SHA>`
- DB: `gitai-exhibit-2026-<元DB名>`
- 隠れるギタイ: `konchu2026_cryptic`／目立つギタイ: `warning_color_fog_v2`
- 世代終了時の「次の人へ交代」は未保存の捕食結果から次世代生成し、IndexedDBの世代番号更新完了を確認してから展示トップへ戻ります。処理失敗時はトップへ戻りません。
- 管理者用パスコードは初回起動時に**設営者が設定**し、以後管理画面への再入場に要求します。オフラインのブラウザパスコードなので不正改造に対する強い認証ではありません。アクセスガイドを併用してください。


## 展示専用の進化速度（2026-10-22）
- **B設定（50%）**：実際のプレイで次世代を生成する際、`continuous_v1` の各突然変異**発生確率**を一律0.5倍にする（特別な突然変異20%→10%、通常の地色色相小変異30%→15%、模様新生4%→2%）。
- **変えないこと**：変異幅、遺伝・交配・生存による親選抜、模様モジュール、画面／ラウンド仕様、通常Web版の進化設定。
- **目立つギタイの初期20世代**：ここは従来の発生確率のまま独立に無捕食進化させ、来場者がプレイを始める第21世代から低速化する。初期世代の乱数シード形式は変えない。
- 変異率の変更は`exhibit/build.py`が**展示用に複製した** `js/pages_preview.js` のみに適用。通常版の`data/evolution_models/continuous_v1/config.json` は不変。生成された世代の診断ログには `exhibit_mutation_rate_factor: 0.5` を付記。
- **2〜3倍の世代数で擬態完成は保証されません。** 自然選択・遺伝的浮動・初期個体のばらつきにも左右されるため、展示前に複数回プレイして進化速度と5世代ごとの可視変化を確認してください。
- 既存の保存済み世代はそのまま保持し、**更新後に新しく生成する世代**から倍率が適用されます。

## 初期インストール・実機検証（公開後）
1. iPadのSafariで展示URLを開く。オフラインファイル保存済み表示が出ることを確認する。
2. Safari共有メニューから「ホーム画面に追加」、**Webアプリとして開く**をオンにして追加する。
3. ホーム画面の専用アイコンから起動して各モードを1世代以上プレイする。
4. 「次の人へ交代」で保存後にトップへ戻り、両モードの世代番号が独立して進むことを確認する。
5. 管理者画面を開き、パスコードを設定して**各モードを別々のJSONとして**「ファイル」アプリ等にバックアップする。必ず実ファイルを確認する。
6. 機内モードにしてWi-Fiもオフ。ホーム画面アイコンでオフライン起動し、両モードを進める。
7. アプリ終了・iPad再起動後に両モードの世代番号が維持されることを確認する。
8. バックアップJSONの整合性・復元を必ずテストする（テスト終了後は元データに戻す）。特に警告色のライフを検証する。

## 更新動作と運用上の限界（EXH-05）
- 管理者パスコードで制限できるのは、管理画面の「最新版を確認」「ダウンロード済みの更新を適用」ボタンです。Service Workerの自動更新検知・インストール・activationをパスコードで制限するものでは**ありません**。
- 展示トップ（index.html）とモード画面（landing.js）はパスコードと無関係に同じ展示scopeのService Workerを登録します。登録のたびに必ず通信による更新確認が走るとは限りませんが、ブラウザは独立して更新を検出・インストールする場合があります。
- 新版のインストールでは **skipWaitingを呼びません**。旧Workerに制御された画面が開いている通常の状態では、新版はwaitingとなり、プレイ中の切替を抑えます。**全旧clientが終了した後やブラウザ再起動時には、管理者が明示適用しなくても新Workerがactivateされ得ます。** 「管理者操作まで旧版に固定」は保証されません。
- activate時は展示版に限った旧キャッシュを整理し、新版の制御へ移ります。旧版キャッシュの保持を保証するロールバック機構ではありません。ただし、この更新処理はIndexedDBの進化データや保存namespaceを削除・変更しません。OSの保存領域削除リスクは別途残ります。
- 展示中に意図しない版変更を避けるには、**会期前に公開を確定**し、会期中のGitHub Pages更新配信を控え、外部バックアップを事前に保存してください。完全オフライン運用も選択肢ですが、オンライン復帰時・再起動時の更新挙動は実機確認が必要です。
- **厳格な固定が必要になった場合**は、版ごとの不変の配信先と明示承認したリリース経路を別途設計してください。現在のService Worker登録を削除するだけでは厳格な固定を実現できません。配信先を変更するならPWAのscope、相対URL、既存iPadの保存領域/アイコンの移行検証が先に必要です。

## 更新テスト
1. iPhoneテザリングで接続。ホーム画面の展示版アイコンから起動する。
2. 管理者画面→「最新版を確認」。新バージョンの場合、ダウンロード完了の表示を待つ。
3. 「ダウンロード済みの更新を適用」。ゲーム中はこのボタンを表示しない。
4. 再起動して表示バージョンを確認し、機内モードで両モードを動かす。
5. 途中の通信切断を想定して、更新未完了時には旧版が起動することを試験する。
6. **iPad Safari実機検証**：vAを起動したままvBを配信し、PIN未解錠・旧client利用中に勝手に画面が切り替わらないことを確認する。続けて全旧client終了後・ブラウザ終了/再起動後のactive版を確認し、手動承認前の切替可能性を記録する。
7. **通信断とオフライン**：vBの全ファイル取得中に切断した場合の旧版での起動と、機内モード再起動後の両モードの起動・世代番号・ライフの維持を確認する。成功した新版更新後も機内モードで起動し、表示build・キャッシュ内容・保存済み世代の整合を確認する。
8. テストにはバックアップ済みの試験データを使用する。vA→vB、PIN未解錠、旧client開放中/全終了後の結果、端末・OS・Safari/PWA経路を記録する。自動activateのタイミングは端末・ブラウザの挙動に依存し、CIの模擬試験だけでは実証できない。

## 大きな実験のバックアップについて（RE2-EXH-02）
- 管理画面のエクスポートは、同じビルドの復元で使う **150 MiB / 20,000保存エントリ / 350,000構造ノード / 最大ネスト36階層** の上限をファイルの共有・ダウンロードより前に検査します。これにより、復元上限を超えているのに「バックアップを生成しました」と通知する誤成功を防ぎます。
- 上限を超えたときはエクスポートを拒否し、**IndexedDB・画像・DNA・診断履歴・ライフはそのまま保持**します。過去の大容量JSONや現在の進化データを削除しないでください。書き出し不能は安全なバックアップができた状態ではありません。
- この対策は復元可能な大容量形式を追加するものではありません。上限を超える正常な長期実験については、履歴を保持した分割/ストリーミング形式とiPadでの容量・往復確認を別途設計する必要があります。上限内でも画像破損や不正DNAのような内容検証、iPadの実メモリ制約、他タブとの競合は別の監査項目です。
- 展示前に両モードの実データを保存先の「ファイル」アプリ等で確認し、**そのバックアップを隔離したテストDBへ復元できること**を確認してください。原本を上書きしてテストしないでください。

## 分割バックアップv2の検証基盤（RE2-EXH-02、未提供）
- `exhibit/backup_v2.js` は**現時点では管理画面に接続していない**、将来の分割バックアップ用の読み取り専用検証ライブラリです。既存のJSON書出し・復元、IndexedDBスキーマ、通常版、進化モデル、画像保存は変更していません。
- 試験上の形式は索引JSONと、各8 MiB以下・最大2,000項目の分割JSONファイル群です。索引はモード・DB・世代・各ファイル順序・保存ストア・件数・バイト数・SHA-256を保持します。
- 検証はファイル不足・余分なファイル・重複・順序不一致・SHA-256不一致・総件数不一致・世代の参照不一致・現世代60匹の画像/DNAキー不足を拒否します。各パートを順次読み込み、全パートを一つのJSON文字列に結合しません。SHA-256は偶発的破損の検出であって、署名や真贋の証明ではありません。
- **重要：この段階ではv2ファイルの書出し・復元UIはありません。** チェックに成功しても復元許可にはなりません。PNGの実画像デコード、ゲノムの妥当性、旧形式互換、同一時点のアトミックなスナップショット取得、途中失敗時に旧データを保持する復元方式は今後の個別PRで設計・テストが必要です。ファイル分割や個別トランザクションから既存ストアを逐次消去する実装を行ってはいけません。
- v1単一JSONはこれまで通り利用可能です。実機でのv2復元成功はまだ主張できません。

## 分割バックアップv2：逐次書き出し部品（RE2-EXH-02、未運用）
- `exhibit/backup_v2.js` の `writePartsFromRecords(records, options, savePart)` は、**外部から同一時点として提供された**保存レコードをストア名→IndexedDBキーの昇順で逐次処理し、上限8 MiB・2,000項目・350,000構造ノードのいずれかに達する前に個別JSONへ分割してハッシュ付き索引を構築します。書き出し用の全巨大JSONは作りません。
- 既存のv1に合わせ、Blob / ArrayBuffer / TypedArray / Date / 通常のJSON値を型付きの値へ符号化します。途中で入力が不正、分割ファイル保存に失敗、PNGやDNA参照キーが欠損する場合は**完成したmanifestを返しません**。途中まで保存された分割ファイルは使用不可なので破棄が必要です。
- **安全上の重要な未対応点**：この部品はIndexedDBを開かず、実験中のデータを一貫した時点で抽出する手段をまだ備えていません。単純に世代ごとの別トランザクションで読み続ける実装は世代混在の危険があるため禁止です。
- 今回の書き出し部品は管理画面、iPadのファイル保存先、バックアップ復元に接続していません。v2索引/分割ファイルの完全性検証はPR #115で追加したものですが、PNG/DNAの意味的検証と安全な復元は未実装です。**展示運用にv2を使わないでください**。
- CIでは22,172件の模擬保存項目を逐次書き出し、分割ファイルから全件検証できることを確認します。これは実機での巨大履歴のメモリ使用量、IndexedDB同時書込、ファイルアプリ保存、往復復元を保証しません。v1バックアップのUIや上限はそのままです。

## 大容量チェックポイントの隔離実験（RE2-EXH-02・未運用）
- `exhibit/backup_checkpoint_v2.js` は、**現行展示版から一切読み込まれていない試験専用モジュール**です。通常版と展示版のIndexedDB v2（3ストア）に対して、バージョン更新・ストア追加・書き込みは行いません。
- 今後、運用前に承認・移行が必要な専用ストア `backup_v2_stage` が**すでに存在する隔離DB**のみを対象に、原本3ストア＋一時ストアの1つの `readwrite` トランザクションで値を複製します。現世代の参照を同じトランザクションで固定します。世代保存や復元のトランザクションと順序関係が成立する想定です。
- 復元や世代進行が後から発生しても、一時ストア内の確定データは読み込み対象が変わらず、8件などの小さなバッチで読み、分割v2 writerに渡せます。バッチ間でブラウザのIndexedDBトランザクションを閉じられるため、Blobの非同期符号化で原本の読込みトランザクションを不活性化しません。
- 途中で容量不足等が発生した場合、**元のデータにはclear/deleteを行わず、一時コピー全体をロールバック**します。一時保存の識別子は重複不可で、コピー済みの別IDを上書きしません。必要なときの後片付けは指定IDの一時ストア内だけを削除します。
- **現時点で本番利用不可**：別ストアへの複製は空き領域を多く消費し、長い単一トランザクションはiPad Safariで時間がかかり得ます。DBバージョン移行・古いタブの接続・容量/処理時間・異常終了後の一時ファイル回収・`localStorage`にある目立つギタイのライフ・実際のファイル保存と復元は未解決です。
- 今回の自動テストは**イベント/トランザクション模擬**です。実機のIndexedDB/Safariや長期履歴の性能を証明しません。DB移行や管理UIとの接続は安全性の検証とユーザーとの設計相談を終えるまで行いません。

## DBスキーマ更新の安全性確認（RE2-EXH-02・移行未実施）
- **現在の展示DBはv2です。** ゲーム側の `js/pages_preview.js` と管理画面の `admin.js` はv2を指定して開きます。v2の接続コードがあるまま同じDBをv3に更新すると、以後のv2指定openは `VersionError` となりプレイや管理画面を止めるおそれがあります。旧タブの `onversionchange` も確認が必要です。
- `exhibit/backup_upgrade_preflight_v2.js` はこのリスクを明示して**読み取り専用で**状態を調査する、管理画面未接続の独立部品です。DBバージョンを指定せず `indexedDB.open(name)` し、既存の保存ストア、世代番号、エントリ件数、各実行コードの互換バージョンを検査します。DBが存在しない場合の暗黙の新規作成はversionchangeトランザクションを中断します。
- `navigator.storage.estimate()` 相当の推定空き容量は参照できますが、推定値であって一時チェックポイントの確定成功は保証しません。要求されたreadwrite移行、削除、ストア作成、`storage.persist()` は実施しません。検査に合格しても本番移行を許可するものではありません。
- **本番移行はまだ行いません。** 実際にv3を適用する前に、ゲーム・管理画面・その他のDB接続コードを同じバージョンへ統一し、古いタブを閉じ、実機の既存データ保持・blocked/VersionError・更新失敗・長時間負荷試験を行います。Safariの容量不足で原本が失われないことを最優先とし、復元が動作するまでは従来のv1バックアップを維持します。

## 実ブラウザでの隔離DB移行リハーサル（RE2-EXH-02・任意の検証画面）
- 独立した診断ページ：`/Gitai_Lab_Preview/exhibit/backup_rehearsal.html`。HTML内でボタンを押したときだけ処理を開始します。トップ画面・ゲーム・管理画面には導線や自動実行を追加していません。PWAのオフライン配信対象には含まれますが、通常プレイから呼ばれません。
- **展示用の本物のセーブデータを操作しません。** 毎回、暗号学的な乱数から `gitai-backup-rehearsal-<32桁16進>` という別名のテストDBを生成し、名前の形式を強制検査します。展示DBや通常のユーザーデータDBには接続・アップグレード・削除できないコードです。
- テスト用DBにv2の画像60件・DNA60件・世代参照1件・シアター1件（合計122件）を保存し、原本件数と世代参照を検証。次にv3移行を意図的にabortしてv2の原本が残ることを確認し、旧v2接続による `onblocked`、v3で `backup_v2_stage` だけが追加されること、旧v2オープナーの `VersionError` を確認します。
- 続けて**実ブラウザのIndexedDB**で既存の `backup_checkpoint_v2.js` を使って確定スナップショットを複製し、`backup_v2.js` で分割JSONに符号化→ハッシュ・全件検証→一時コピー削除まで試します。いずれも合成データであり、実験データや本番ライフはコピーしません。終了時にテスト専用DBを削除します。中断・ブラウザ強制終了時には隔離DBが残る場合がありますが、本番DBは変更されません。
- **検証が成立する範囲**：SafariやiPad上でv2→v3の基本挙動、DBバージョン非互換、122項目の複製・分割・後片付けを再現できます。ただし、本番の数万件以上・iPadの保存容量、バックグラウンド中断、実画像の意味的妥当性、復元、localStorageのライフ同期は別の検証が必要です。自動CIはNodeのモデル/静的検査のみであり、Safari/iPad実機で成功したと主張しません。
- 本番DBをv3に上げる実装は**まだ行っていません**。ゲーム・管理画面・シアターを含めて同時にDBバージョンの整合をとった上での互換性審査が別途必要です。実データの復元試験を終えるまで、本番移行は承認しない方針です。

## 分割バックアップv2の内容検証（RE2-EXH-02・隔離部品）
- `exhibit/backup_restore_preflight_v2.js` は**DBを一切開かず・書き換えず**、全パートのハッシュ／構造検証に加えて、各レコードの型タグとバイナリ符号化（Blob/ArrayBuffer/TypedArray/Date）を厳格に確認します。未対応の型・不正なBase64・壊れた配列・日付・危険なプロパティ名を拒否します。
- **現在世代60匹のDNAとPNGは、既存v1管理画面と同じ厳格な検査関数を必ず渡す**設計です。これらが欠けていれば検査を中断します。ハッシュが正常でもPNGや対立遺伝子が不正なら失敗します。古い履歴のDNAには現在のモデルを無理に適用せず、全履歴の型タグのみ確認します。
- CIで、v1の実際の`checkGenome`・`checkMothPng`を抽出して模擬PNGをデコードするテストを行います。両モードの123件の分割ファイルを検証し、破損・改ざん・検査関数欠落を拒否することを確認します。
- **注意**：本機能は管理画面や本番DBには接続しておらず、`safeToRestore: false`を返します。検証結果だけでは原子的な全件復元、ストレージ容量、実機Safariでの画像デコード、`localStorage`のライフ整合を保証しません。現行v1の書出し・復元手順は変更していません。

## 分割バックアップv2：隔離DBでの原子的復元試作（RE2-EXH-02・本番利用禁止）
- `exhibit/backup_restore_atomic_v2.js` を追加しました。**DB名が `gitai-backup-rehearsal-`＋32桁の16進数で、バージョン3かつ専用一時ストアを持つDB以外は全て拒否**します。本物の展示DB、通常プレイ用DBへの使用は禁止・不可能なコードになっています。ゲーム・管理画面・診断画面からも自動起動されません。
- 分割ファイルを全件ハッシュ・PNG・DNA検証（PR #122の読み取り専用機能）した後、再検証しながら**一時ストアだけ**へ複数の短いトランザクションで取り込みます。途中の容量不足や後続ファイル破損は一時ストアを後片付けし、原本には触れません。
- 検証済み・取り込み済みの一時データを最後に元ストアへ反映する処理は、**images／meta／theater_frames／一時ストアを含む1つのIndexedDB readwriteトランザクション**です。古いデータのclear→新データput→`restore_epoch`の新しい乱数への更新をその中で完了させます。欠損、容量不足、破損があれば全操作をabortするため、原本のclearだけが成功してしまうことを防ぎます。
- CIの隔離DBイベント模擬では、122件の正常復元、途中QuotaExceededError、欠損や世代参照不一致、破損データ、後続パート改ざん、取消時の原本保持、一時データの削除、epochローテーションを検証します。**この試験は実機Safari上での大容量トランザクション・ストレージ不足を証明するものではありません。**
- 別に保存されている「目立つギタイ」のライフ（localStorage）は復元せず、`lifeRestored:false` と明示します。一時ファイルの後片付けに失敗した場合もDB復元の成功と混同しません。本番移行には専用一時ストアの安全な準備、実機検証、ライフ同期、ユーザー操作、バックアップファイル選択UI、長時間データの復旧戦略が引き続き必要です。
- **重要**：この段階のテストはあくまで復元の原子性を検証するための土台です。通常の管理画面から大容量バックアップを復元できるようになったわけではありません。既存のv1バックアップ機能や進化データの構造は一切変更していません。

## iPad Safari実機用・原子的復元の隔離テスト（RE2-EXH-02、未実証）

- Node CIは隔離用名前の強制、通常画面からの非接続、ボタン経由のみの実行、テスト内の中断注入・構文などを確認します。**iPad Safari実機で試験ボタンを押して成功したという実測結果はまだありません。** 検証時は通常の展示セーブデータを初期化・削除しないでください。

## 警告色モードのライフ復元・二重保存対策（RE2-EXH-02・隔離試作）
- 「目立つギタイ」のライフは、世代やDNAを持つIndexedDBとは**別のlocalStorage**に記録されています。2つの保存領域は単一トランザクションで同時に確定できません。DB復元に成功してもライフの書込みに失敗した場合、DBは巻き戻せず、**部分成功（ライフ未完了）**として扱う必要があります。
- `exhibit/backup_warning_life_recovery_v2.js` は**隔離DBだけ**を対象とする独立部品です。名前が`gitai-backup-rehearsal-`＋32桁乱数、バージョン3のDBのみを受け付けます。本番用の`gitai-warning-life-v1:`キーは使用せず、`gitai-warning-life-sandbox-v2:`＋隔離DB名にしかライフを書き込みません。通常画面やadmin.jsからは読み込まれません。
- 分割索引が警告色モード・同じDB・同じ世代・同じ件数を示し、DB復元が確定したことを確認した後、`meta.current_generation_id`と`meta.restore_epoch`を読み取ります。どちらかが変わっていれば古いライフは再適用しません。ライフの値は1〜30の整数（三分割単位）、世代番号と一致することを確認します。ライフ値がnullの場合は、古い一時ライフを削除します。
- `localStorage`への書き込みエラー・読み出し不一致は`life-pending`として報告し、同じ世代とepochが継続しているときだけ再試行できます。新しい復元・世代進行が判明した場合は`stale`とし、古いライフを適用しません。
- Safariでの隔離確認用に`backup_rehearsal.html`の**「隔離ライフ復元テストを実行」**ボタンを追加しています。専用DBに合成の世代とepochを作り、合成ライフ（7/30）で失敗→再試行→古いepoch拒否をテストし、最後にテストDBと専用localStorageキーを削除します。**実際の警告色モードや本人の保存データには触れません。**
- **重要な限界**：本テストが通っても、`IndexedDB`読出しから`localStorage`書込みまでの間に別タブが進行すれば完全な整合は保証できません。他のプレイタブを閉じる管理者操作、ライフの本番復旧処理、DBとライフの監査、実機の容量・強制終了試験は今後の課題です。現行v1復元や通常のライフ挙動は一切変更しません。CIは合成データの模擬テストであり、iPad実機試験の完了を意味しません。

## バックアップ中の別タブ操作に関する注意（EXH-F02）
- エクスポート時は、images・meta・theater_frames を**同一のIndexedDB readonly transaction**で読み、同じ確定時点のデータを取得してからJSONへ符号化します。複数storeを別々に読み取ることによる世代の混在を防ぎます。
- 復元は3store一括のreadwrite transactionで行い、毎回新しいランダムな `restore_epoch` をmetaへ同時に確定します。更新済みの展示ゲームは最初の世代読込前にepochを1度取得し、同じ世代IDであっても世代保存transaction内のepochが違えば**古い計算の確定を拒否**します。復元済みデータは変更せず、古いタブには再読み込みが必要です。
- 安全のため、管理者はバックアップ・復元前に両モードのゲーム画面と他の展示タブを終了し、進化結果と世代保存の完了を確認してください。別タブを開いたままのexport/restoreやiPad実機の同時実行は未検証です。
- **残る限界**：epoch判定を知らない旧バージョンのゲームタブや、独立したlocalStorageのライフ情報の同時変更までは保護できません。旧タブが開いたまま新コードを展開・復元しないでください。Safari/iPad実機2タブでのABA復元・世代中断・ライフ整合は未検証です。管理者は従来どおり他のゲームタブを閉じてから復元してください。

## データ保全の限界
- IndexedDBとCache StorageはOSの空き容量・利用状況やユーザー操作で消える可能性があります。永続ストレージ要求が許可されてもバックアップは必要です。
- iPadホーム画面アプリとSafariタブは保存領域が分離されることがあります。展示運用は常に同じホーム画面アイコンを使ってください。
- JSON復元はバックアップのチェックサム・モード・現在世代の画像枚数を検証したのち、**モードごとの全オブジェクトストアを1つのIndexedDBトランザクション**で更新します。エラー時はトランザクションをロールバックします。警告色のライフは別のlocalStorage保存なので、異常時には個別の復旧確認が必要です。
- OSストレージ削除・PWA削除・初期化はゲーム側だけでは防げません。バックアップをiPadの外部にも保管してください。
- 更新失敗時は既存の有効なService Workerを残す設計です。**更新適用後に実機の完全オフライン起動テストを必ず実施**してください。
