# 昆虫大学2026：iPad不在時のデータ保護・性能・電源監査（2026-11-05）

対象：展示版GitHub Pages（`/exhibit/`）。調査時点の公開 `main`：`9d2baf31a5f82f4b6521b49c6e7e1a189c34c426`。  
この資料はコード上の根拠と実機結果を分けて記録する。iPadの電力・速度・OSのストレージ保持をコードだけで「合格」としない。

## 1. すでに利用者が実機で確認したこと（再試験は変更箇所だけ）

- 進化シアター：ニックネームの「〇〇のプレイ」と画像内右上の配置、世代終了後／モード選択からの表示。PR #223、#224、#225 公開後のユーザー報告で正常。
- 完全オフライン起動と両モード利用、PWA終了・再起動後の進化データ保持：ユーザー報告で正常。
- 長時間待機・スリープ後のBGM／効果音：ユーザー報告で正常。未発生の「毒／死亡」音を個別に再現したとは断定しない。
- 1人5世代、途中／次来場者交代、進化データ継続、目立つギタイのライフ継承と交代時10回復：ユーザー報告で正常。
- 2026-10-28の隔離合成v2バックアップ：3/3試験、6個のファイル再選択、SHA-256と122件一致が実機合格。**本番のv2書出し・復元機能ではない**。
- iPadの充電が、18W表示のSmart Connector充電器を単独で使っても減ることがある。原因は未特定。**給電の実測は未合格**。

## 2. 本番バックアップの現状と限界

**現在の実データの書出し／復元はv1 JSON。** `exhibit/admin.js` に上限チェックがある：

- 20,000保存エントリ、150 MiB、350,000構造ノード、入れ子36階層。
- 書出し前に件数を確認し、画像・DNAの一致を検証し、全体整合性に失敗すればファイルの成功扱いをしない。
- 「保存準備」「共有シートを出した」はファイル保存の証明ではない。iPad「ファイル」等に保存された実体を再選択し、読み取り専用の検証で成功を確認する。
- 保存件数が**16,000件以上**に近づいた場合、管理画面の読み取り専用診断で早期に警告する改善を本PRで用意した。**件数が16,000件未満でも容量・ノードで失敗する可能性は残る。**
- 上限や容量不足でエラーが出たら、元の進化データ・古いJSONを消さない。仕様未完了のv2を勝手に実データに接続しない。

### 20,000件＝約160世代、と短絡してはいけない理由

`js/pages_preview.js` の通常の世代コミットは、新しい世代60匹の画像と60匹のDNAを保存した後、**初代を除く前世代の画像・DNAを削除する**。一方、各世代の進化シアター画像、診断・完了ログは蓄積する。残存件数は純粋な「世代数×120」ではない。標本／追加メタ情報／失敗した保存の記録も影響する。

大きな実データで先に制限になり得るのは、件数上限だけでなく**進化シアター画像を含むJSON全体のバイト数**とノード数である。世代あたりのWebP容量は模様と背景で変わり、iPadOSの使用可能容量・CPU／メモリをソースコードだけでは見積もれない。正確な予測には管理画面の実件数・使用量表示と、**実際に保存したv1ファイルのサイズ**が必要。

### 分割バックアップv2（まだ本番に導入しない）

- `backup_v2.js`：8MiB以下のパート、最大250,000件などの書出し・SHA-256検証コードがある。
- `backup_checkpoint_v2.js`：原データと別に`backup_stage`ストアへコピーする。**ゲームの既存DB v2にはこのストアがない**。新スキーマの設計・移行と、iPadでの一時容量の試験が必要。
- `backup_restore_preflight_v2.js` と `backup_restore_atomic_v2.js`：元の画像/DNAの厳格な検査と隔離DB向けの安全な原子的復元試験。後者は実験DB名では動かないよう制限している。
- 既存CI：22,172件の純粋な書出しと再読込み、途中停止、ファイル破損、複数タブ競合、容量不足想定などの試験あり。
- 今回追加：**第5001世代、過去1000世代のシアター画像、初代／現世代の各60 PNG・DNA、警告色ライフ**を模した独立データで、分割writerとSHA検証を実行。これは**合成データ**で、実iPadで1,000世代を復元できたという意味ではない。
- 既存PR #219で準備されていた本番v1コーデックの独立テストも最新のニックネームキーに合わせて移植。**シアター履歴1,000枚と日本語・絵文字を含む参加者名200件**を実際の`admin.js`の符号化・復号で照合する（合成・メモリ上のみ）。

**v2本番導入の残るゲート：** 本番の一貫したスナップショット取得、容量不足でも原データが安全な実機検証、分割ファイルのiPad「ファイル」への保存→再選択、バージョン変更と既存v1バックアップの互換性、途中停止／再起動からの保護。実データを上書きして復元試験しない。Issue #163 を開いたまま管理する。

## 3. 性能・電源：iPad無しで確定できる範囲

- タイトルの虹色波紋：入力後のみ約1.75秒の連続描画。待機中に常時再描画する処理ではない（`js/entertainment_portal.js`）。
- 捕食エフェクト：約260msで終了する連続描画。放置中の常時描画ではない（`index.html`）。
- 目立つギタイ・霧：ゲーム中の霧イベントに限り、`requestAnimationFrame`でコールバックを予約し、描画は設定上15fps、背景ぼかしと3つのグラデーションを使う。**霧のあるラウンドではGPU／CPU負荷の候補**だが、ラウンド終了／バックグラウンド時には止める処理あり。
- 画面Wake Lock：ゲーム読み込み後、開始時、アプリ復帰時に画面スリープ防止を要求する。展示向けだが画面点灯の電力消費に寄与する。
- 展示BGM：`exhibit/ambient_ios.js`はAACプレーヤー1つ＋550ms毎の復旧確認。効果音は別系統。繰り返し音声再生の電力はあるが、これだけで18W給電を超えると断定できない。
- PF06：標本のバッチ描画、シアターのBlob URL数制限は実装済み。試験ページは100／1000件の**隔離合成データ**。iPadでの実速度と温度は未確認（Issue #146）。

## 4. iPadが戻ってからの最小限の残試験（スクリーンショット原則不要）

1. **電源**：同じ18W磁気充電器で画面OFF 30分、続いて画面輝度約50％・ゲーム表示中30分、それぞれ開始／終了％、充電マーク、端末が熱いか記録。音・バックグラウンドアプリ等の条件は可能な限り揃える。発熱時に無理に長時間続けない。
2. **PF06**：隔離ページ `/exhibit/pf06_perf_rehearsal.html` の100件と1000件の測定結果を文字で共有。実験DBとは別の合成DBであり、実データを消さない。時間／エラーだけでよい。
3. **容量**：管理者用で各モードの「保存状況を診断（読み取り専用）」を押し、現在世代、画像・DNA・シアター件数、サイト全体の使用量概算があれば記録する。**今回は現在のテストデータの実ファイル再提出不要**。本番開始後のバックアップは別件で確実に実ファイル保存・検証する。

以前合格した両モードの5世代交代・効果音・進化シアターを再び長時間テストしない。バッテリー減少とPF06のみ実機でないと完了できない。

## 5. リリース判断・巻き戻し

このPRは読取り専用診断の表示改善・合成試験・運用文書だけ。遺伝・描画・ゲームセーブ・DBバージョン・v1書出し／復元・v2本番化は変更しない。PR CIが成功するまでは統合しない。CI成功は展示iPadで新ビルドを受入れた証明ではない。展示本番中は不必要なGitHub Pages更新を止め、実データの保持を最優先にする。
